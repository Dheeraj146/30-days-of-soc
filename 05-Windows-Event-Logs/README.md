# Day 5 — Windows Event Logs

## 🎯 Objective

The objective of Day 5 is to understand Windows Event Logs as a primary source of security telemetry for SOC operations.

Windows continuously records authentication, process, account, service, system, application, and security activity as events. These events can be collected into a SIEM, correlated with endpoint and network telemetry, used to create detections, and analyzed during incident response.

The goal is not simply to memorize Event IDs. A SOC analyst must understand what generated an event, what fields it contains, what happened before and after it, and whether the observed activity is expected in the environment.

---

## 1. What Is a Windows Event?

A Windows event is a recorded occurrence generated by Windows, an application, a service, or another software component.

Examples include:

- Successful user logon
- Failed authentication
- Process creation
- Service installation
- Scheduled-task changes
- User-account creation
- Group-membership changes
- PowerShell activity
- System startup and shutdown
- Security-policy changes

A simplified event contains:

~~~text
Event
 ├── Timestamp
 ├── Provider
 ├── Event ID
 ├── Level
 ├── Computer
 ├── User / Security Context
 └── Event Data
~~~

An Event ID alone is rarely enough to determine whether activity is malicious.

---

## 2. Why Event Logs Matter in a SOC

Suppose a SIEM reports:

~~~text
Suspicious activity detected on WORKSTATION01
~~~

The alert may not explain the complete story.

Windows telemetry can help answer:

- Which user was involved?
- When did authentication occur?
- Was the login successful?
- Was it local or remote?
- Which process executed?
- Which account was created or modified?
- Was a privileged group changed?
- Was PowerShell used?
- Did a service or scheduled task appear?
- Did security controls change?

The analyst correlates these events with EDR, firewall, DNS, proxy, Active Directory, and SIEM telemetry.

This transforms isolated records into an investigation timeline.

- Windows Logs
- Applications and Services Logs

Common Windows Logs include:

- Application

## 4. Windows Event Log Architecture

A simplified architecture is:

~~~text
Windows Component / Application
          ↓
      Event Provider
          ↓
      Event Channel
          ↓
   Windows Event Log
          ↓
      Collector
          ↓
         SIEM
          ↓
      SOC Analyst
~~~

### Event Provider

The provider is the component responsible for generating an event.

Examples include:

- Microsoft-Windows-Security-Auditing
- Microsoft-Windows-PowerShell
- Microsoft-Windows-Sysmon
- Service Control Manager

### Event Channel

A channel is a logical destination for events.

Examples include:

- Security
- System
- Application
- Microsoft-Windows-PowerShell/Operational
- Microsoft-Windows-Sysmon/Operational

### Event ID

The Event ID identifies the event type within a provider.

For example, Security Event ID 4624 represents a successful logon.

---

## 5. Event Levels

Common Windows event levels include:

- Critical
- Error
- Warning
- Information
- Verbose

Event level is not the same as maliciousness.

A successful authentication may be informational but extremely important during an investigation. An error may be completely benign.

Security relevance comes from the event content and surrounding context.

---

## 6. Windows Security Log

The Security log is one of the most important Windows logs for SOC operations.

Depending on audit configuration, it can contain events related to:

- Authentication
- Account management
- Privilege use
- Security-policy changes
- Object access
- Process activity
- Group membership
- Logon and logoff

The available telemetry depends on the organization's audit configuration.

---

## 7. Audit Policy

Windows does not automatically record every possible security event.

Audit policy determines which categories of activity are recorded.

Important categories include:

- Account Logon
- Logon/Logoff
- Account Management
- Policy Change
- Privilege Use
- Detailed Tracking
- Object Access
- System

The relationship is:

~~~text
Required detection
       ↓
Required telemetry
       ↓
Correct audit configuration
       ↓
Event collection
       ↓
Reliable investigation
~~~

If the required telemetry was never enabled or collected, an analyst may not be able to reconstruct an activity later.

## 9. Event ID 4624 — Successful Logon

Event ID 4624 indicates a successful logon.

Useful fields may include:

- Account name
- Account domain
- Logon ID
- Logon Type
- Source network address
- Authentication package
- Workstation information
- Security identifier

An analyst should ask:

- Which account logged in?
- Which host received the logon?
- Where did the request originate?
- What was the Logon Type?
- Was the account expected to access this system?
- What happened immediately afterward?

A successful logon is normal activity in most environments. Context determines whether it requires investigation.

---

## 10. Event ID 4625 — Failed Logon

Event ID 4625 indicates a failed logon.

It can be useful for investigating:

- Brute-force attacks
- Password spraying
- Incorrect credentials
- Misconfigured services
- Suspicious remote access

Example:

~~~text
Many failed logons
       ↓
Same source
       ↓
Multiple accounts
       ↓
Short time period
~~~

This pattern may warrant investigation.

However, failed authentication can also be caused by expired passwords, users entering incorrect credentials, applications using stale passwords, or misconfigured services.

## 11. Windows Logon Types

Common logon types include:

| Logon Type | Meaning |
|---:|---|
| 2 | Interactive |
| 3 | Network |
| 4 | Batch |
| 5 | Service |
| 7 | Unlock |
| 8 | NetworkCleartext |
| 9 | NewCredentials |
| 10 | RemoteInteractive |
| 11 | CachedInteractive |

### Type 2 — Interactive

Usually associated with a local console logon.

### Type 3 — Network

Commonly associated with network access to a resource.

### Type 5 — Service

Associated with a service using a configured identity.

### Type 10 — RemoteInteractive

Commonly associated with Remote Desktop Services/RDP.

### SOC relevance

Logon Type adds context to an authentication event. For example, an unexpected Type 10 logon involving a privileged account can deserve additional investigation.

---

## 12. Event ID 4672 — Special Privileges Assigned to New Logon

Event ID 4672 indicates that special privileges were assigned to a new logon.

It may appear during legitimate administrative sessions.

Potentially sensitive privileges can include:

- SeDebugPrivilege
- SeBackupPrivilege
- SeRestorePrivilege
- SeTakeOwnershipPrivilege

4672 is not automatically malicious.

Correlate it with:

- User
- Logon ID
- Source
- Host
- Authentication time
- Process creation
- Administrative actions

---

## 13. Event IDs 4634 and 4647 — Logoff

Event ID 4634 indicates that a logon session was terminated.

Event ID 4647 indicates a user-initiated logoff.

These events help establish session timelines.

Example:

~~~text
10:00  → 4624 Successful Logon
10:02  → 4688 Process Created
10:05  → Network Activity
10:20  → 4634 Logoff
~~~

The sequence provides more context than analyzing each event independently.

---

## 14. Event ID 4688 — Process Creation

Event ID 4688 indicates that a new process was created when the relevant auditing is enabled.

This is one of the most important Windows endpoint events.

Useful information can include:

- New process name
- Process ID
- Parent process
- Creator process
- Account context
- Command line, when configured

Example:

~~~text
explorer.exe
      ↓
powershell.exe
      ↓
cmd.exe
      ↓
whoami.exe
~~~

Process creation becomes significantly more useful when correlated with the user, command line, file path, network connections, and parent process.

---

## 15. Command-Line Logging

Knowing only the executable name may not be sufficient.

For example:

~~~text
powershell.exe
~~~

could represent legitimate administration or malicious activity.

A command line provides additional context:

~~~text
powershell.exe -File C:Scriptsackup.ps1
~~~

versus:

~~~text
powershell.exe -EncodedCommand ...
~~~

The command-line content should be interpreted together with user, parent process, destination, script content, and timing.

---

## 16. Event ID 4697 — Service Installed

Event ID 4697 indicates that a service was installed when the appropriate auditing is enabled.

Services have legitimate administrative uses, but attackers can also abuse them for persistence or privileged execution.

Investigate:

- Service name
- Service account
- Executable path
- Creating account
- Creation time
- Parent process
- Whether the service is expected

---

## 17. Scheduled Task Events

Important scheduled-task events include:

- 4698 — Task created
- 4699 — Task deleted
- 4700 — Task enabled
- 4701 — Task disabled
- 4702 — Task updated

A scheduled task can be legitimate automation or an attacker persistence mechanism.

A useful correlation is:

~~~text
Task Created
     ↓
Script / Executable
     ↓
Process Execution
     ↓
Network Connection
~~~

## 18. Account Management Events

Important examples include:

- 4720 — User account created
- 4722 — User account enabled
- 4724 — Password reset attempt
- 4725 — User account disabled
- 4726 — User account deleted

If a new account appears on a production server, determine:

- Who created it?
- When?
- Why?
- Was the creation authorized?
- Which groups was it added to?
- Did it log in?
- What did it execute?

Account creation becomes more meaningful when correlated with subsequent activity.

---

## 19. Group Membership Changes

Important events include:

- 4732 — Member added to a local security-enabled group
- 4733 — Member removed from a local security-enabled group

A useful investigation pattern is:

~~~text
Normal User
    ↓
Added to Local Administrators
    ↓
Privileged Logon
    ↓
Administrative Process
~~~

The analyst must determine whether the change was legitimate or unauthorized.

---

## 20. Event ID 4740 — Account Lockout

Event ID 4740 indicates that a user account was locked out.

Repeated lockouts can result from:

- Brute-force attempts
- Password spraying
- Stale credentials
- Misconfigured applications
- Scheduled tasks using old credentials

Investigate:

- Target account
- Caller computer
- Time
- Frequency
- Related 4625 events
- Related successful logons

---

## 21. Event ID 4776 — Credential Validation

Event ID 4776 is associated with credential validation by a domain controller.

It can be useful when investigating:

- NTLM authentication
- Repeated credential validation
- Authentication failures
- Account abuse

It should be correlated with other authentication events and the identity infrastructure.

---

## 22. Event ID 1102 — Security Audit Log Cleared

Event ID 1102 indicates that the Security audit log was cleared.

Clearing logs can be legitimate administrative activity, but unexpected clearing can also be a defense-evasion indicator.

Investigate:

- Account that cleared the log
- Timestamp
- Host
- Activity immediately before the event
- Process execution
- Privilege use
- Other security-control changes

A useful timeline may be:

~~~text
Suspicious Logon
      ↓
Privileged Activity
      ↓
Command Execution
      ↓
Security Log Cleared
      ↓
Further Activity
~~~

### Application Log

Contains events generated by applications and software components.

Examples:

### System Log

Contains events generated by Windows system components.

Examples:

## 24. PowerShell Logging

A commonly used PowerShell channel is:

~~~text
Microsoft-Windows-PowerShell/Operational
~~~

Useful event IDs include:

- 4103 — Module Logging
- 4104 — Script Block Logging

PowerShell is widely used legitimately, so a PowerShell event is not automatically malicious.

Investigate context such as:

- User
- Parent process
- Script content
- Command line
- Encoded commands
- File creation
- Network activity
- Child processes

---

## 25. Event ID 4104 — Script Block Logging

Event ID 4104 can record PowerShell script-block content when Script Block Logging is enabled.

This can provide substantially more visibility into what PowerShell code executed.

A possible investigation chain is:

~~~text
User Logon
     ↓
PowerShell Process
     ↓
4104 Script Content
     ↓
File Creation
     ↓
Network Connection
~~~

The event should still be interpreted in context.

---

## 26. Event ID 4103 — Module Logging

Event ID 4103 can provide information about PowerShell module activity when Module Logging is configured.

Module Logging and Script Block Logging provide different types of visibility and can complement one another.

SOC teams may enable both depending on their security and logging requirements.

- Keywords

## 28. Querying Events with PowerShell

PowerShell provides the Get-WinEvent cmdlet.

Recent Security events:

~~~powershell
Get-WinEvent -LogName Security -MaxEvents 20
~~~

Successful logons:

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624}
~~~

Failed logons:

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625}
~~~

Process creation:

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4688}
~~~

Multiple Event IDs:

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624,4625,4688}
~~~

Time-based query:

~~~powershell
Get-WinEvent -FilterHashtable @{
    LogName='Security'
    StartTime=(Get-Date).AddHours(-1)
}
~~~

---

## 29. XPath Filtering

More precise event filtering can be performed using XML/XPath queries.

Example:

~~~powershell
Get-WinEvent -FilterXPath "*[System[(EventID=4625)]]" -LogName Security
~~~

XPath filtering becomes useful when a SOC analyst needs to combine conditions involving Event IDs, providers, timestamps, or event fields.

---

## 30. Event XML

Windows events are structured records.

A PowerShell query can expose event details:

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624} -MaxEvents 1 |
    Format-List *
~~~

The XML representation can expose fields that are not immediately obvious in the standard Event Viewer display.

This matters because SIEM platforms parse these structured fields into searchable data.

---

## 31. Event Record ID

Each event log maintains a record identifier.

Record IDs help distinguish events within a particular log and can assist with investigation ordering.

However, a Record ID is local to its event log. It should not be treated as a universal identifier across all Windows systems.

---

## 32. Timestamp Analysis

Time is critical during incident response.

Example:

~~~text
09:41:02  Successful Logon
09:41:08  PowerShell Started
09:41:10  Script Block Logged
09:41:15  File Created
09:41:22  Network Connection
09:42:01  Scheduled Task Created
~~~

The sequence can reveal relationships that are not visible from individual events.

Always consider:

- Host time zone
- Clock accuracy
- SIEM time normalization
- Event generation time
- Event collection time

Clock differences can create misleading timelines.

---

## 33. Event Correlation

The real value of Windows Event Logs appears when multiple events are correlated.

Example:

~~~text
4624
Successful Logon
      ↓
4688
PowerShell Created
      ↓
4104
Script Activity
      ↓
File Activity
      ↓
Network Connection
      ↓
4698
Scheduled Task Created
~~~

No single event necessarily proves compromise.

Together, these records may provide substantially stronger evidence.

The core SOC principle is:

> **Do not investigate events in isolation. Investigate relationships between events.**

## 34. Authentication Investigation Workflow

Suppose there are repeated failed logons.

### Step 1 — Identify 4625 events

~~~powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625}
~~~

### Step 2 — Extract source information

Review:

- Source IP
- Account
- Workstation
- Logon Type
- Authentication package

### Step 3 — Determine frequency

Ask:

- How many attempts?
- Over what period?
- Against one account or many?

### Step 4 — Check successful authentication

Search for 4624 events involving the same account or source.

### Step 5 — Investigate post-authentication activity

Look for:

- 4688 process creation
- 4672 privileged activity
- Account changes
- Network activity
- Persistence

## 35. Process Investigation Workflow

When a suspicious process is detected, investigate Event ID 4688 where available.

Review:

1. Process name
2. Process path
3. Process ID
4. Parent process
5. Creator process
6. User account
7. Command line
8. Timestamp
9. Related network activity
10. Related file activity

A simplified workflow is:

~~~text
4688
  ↓
Process
  ↓
Parent
  ↓
User
  ↓
Command Line
  ↓
File
  ↓
Network
  ↓
Persistence
~~~

This is a fundamental endpoint-detection workflow.

## 38. Windows Event Logs and SIEM

A SOC normally does not manually inspect Event Viewer on every endpoint.

A SIEM can collect and centralize Windows telemetry.

Example:

~~~text
Windows Endpoint
       ↓
Windows Event Logs
       ↓
Agent / Forwarder
       ↓
SIEM
       ↓
Parsing / Normalization
       ↓
Correlation Rules
       ↓
Alert
       ↓
SOC Analyst
~~~

Common platforms include:

- Wazuh
- Splunk
- Microsoft Sentinel
- Elastic Security

Centralization allows analysts to search across many endpoints and correlate events at scale.

## 39. Windows Event Forwarding

Windows environments can use Windows Event Forwarding (WEF) to forward events from source computers to a collector.

Conceptually:

~~~text
Endpoint 1 ─┐
Endpoint 2 ─┤
Endpoint 3 ─┼──→ Event Collector
Endpoint 4 ─┘          ↓
                       SIEM
~~~

This centralizes telemetry and reduces the need to inspect each endpoint individually.

## 40. Event Logs and Detection Engineering

Event Logs are raw material for detections.

Example:

~~~text
4625
Multiple failed logons
      +
Same source
      +
Short time window
      ↓
Potential brute-force detection
~~~

Another example:

~~~text
4688
PowerShell
      +
Suspicious command line
      +
Unexpected parent
      +
External network connection
      ↓
Investigation alert
~~~

Detection logic should consider environment context and thresholds to reduce false positives.

---

## 41. False Positives

Event-based detections can generate false positives.

Examples:

- Administrators legitimately using PowerShell
- Automated services generating failed authentication
- Scheduled tasks executing expected scripts
- Security software creating services
- IT administrators modifying groups

Therefore:

~~~text
Event ID 4688 = Malicious
~~~

is not a valid detection by itself.

Good detection engineering combines multiple conditions and contextual information.

## 52. SOC Investigation Scenario

Imagine a SIEM generates:

~~~text
Multiple failed logons detected
~~~

The SOC analyst should not immediately close or escalate the alert.

### Phase 1 — Validate

Review:

- Event ID
- Account
- Source
- Logon Type
- Time period

### Phase 2 — Scope

Determine:

- Number of attempts
- Number of accounts
- Number of systems
- Source addresses

### Phase 3 — Correlate

Search for:

- 4624 successful logons
- 4672 privileged activity
- 4688 process creation
- Account changes
- Network activity

### Phase 4 — Timeline

Construct:

~~~text
Failed Authentication
        ↓
Successful Authentication?
        ↓
Process Creation
        ↓
Privilege Activity
        ↓
Network Activity
        ↓
Persistence
~~~

### Phase 5 — Document

Record the evidence, affected systems, relevant accounts, timeline, investigation findings, and the action taken according to the organization's incident-response process.

The Event ID is the beginning of the investigation, not the conclusion.

## 53. Common Mistakes

### Mistake 1 — Treating every event as malicious

Most Windows events are normal operating-system activity.

### Mistake 2 — Looking only at Event ID

The same Event ID can have different significance depending on account, host, source, time, and surrounding events.

### Mistake 3 — Ignoring Logon Type

Authentication events become much more useful when the Logon Type is understood.

### Mistake 4 — Ignoring process lineage

A process name without its parent process loses important context.

### Mistake 5 — Ignoring time

Event order often provides critical investigative clues.

### Mistake 6 — Trusting one source

Endpoint, identity, network, and SIEM telemetry should be correlated.

### Mistake 7 — Assuming missing events mean nothing happened

Logging may be disabled, filtered, overwritten, or never collected.

## 54. SOC Analyst Investigation Model

A useful model is:

~~~text
WHO?
 ↓
Which user/account?

WHAT?
 ↓
What happened?

WHEN?
 ↓
What time?

WHERE?
 ↓
Which host/source?

HOW?
 ↓
Which process/logon mechanism?

WHAT NEXT?
 ↓
What happened afterward?

SCOPE?
 ↓
Did it happen elsewhere?
~~~

This model can be applied to authentication, process execution, account changes, persistence, and many other Windows investigations.

## 🔍 SOC Analyst Perspective

Windows Event Logs are the language through which many endpoint activities become visible to a SOC.

When an analyst sees:

~~~text
4624 → Successful Logon
~~~

the correct question is not simply "Who logged in?"

The analyst should determine:

- Which user?
- From where?
- To which host?
- What Logon Type?
- At what time?
- Was the account privileged?
- What happened afterward?

If the next event is:

~~~text
4688 → PowerShell
~~~

the investigation expands:

- Who launched PowerShell?
- What was the parent process?
- What command line was used?
- Was script logging enabled?
- Did 4104 reveal script content?
- Did the process create files?
- Did it connect to the network?

If subsequent events include 4698 or 1102, the analyst has additional evidence that requires correlation.

The core principle is:

**An event is a piece of evidence. Correlation turns evidence into an investigation narrative.**
